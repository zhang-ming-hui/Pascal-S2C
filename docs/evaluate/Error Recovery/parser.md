| 策略名称 | 工作原理 | 优点 | 缺点 |
| :--- | :--- | :--- | :--- |
| **1. 恐慌模式恢复**<br>(Panic-Mode Recovery / 紧急方式恢复) | 发现错误后，不断丢弃输入符号，直到遇到预先设定的**同步标记**（如分号 `;`、右大括号 `}` 或 `end` 等语句结束符）。 | - 实现简单，代码量少。<br>- 保证分析器不会陷入死循环。 | - 可能跳过大量有效代码，导致后续关联错误被掩盖。<br>- 丢失上下文信息较多。 |
| **2. 短语层次恢复**<br>(Phrase-Level Recovery) | 对错误发生点的输入流进行**局部修正**。通过替换、插入或删除少量 Token（如自动补全缺失的分号 `;`）来尝试修复序列。 | - 比恐慌模式更精细，保留了更多代码信息。<br>- 能快速纠正常见的细小拼写或标点错误。 | - 难以覆盖所有错误情况，边界条件复杂。<br>- 修正策略若设计不当，容易在当前位置反复插入字符导致**死循环**。 |
| **3. 错误产生式**<br>(Error Productions) | 在语法规则中**预埋**针对常见错误的产生式。例如允许 `if x > 0`（无括号）匹配特定的错误规则，从而识别并跳过。 | - 错误诊断信息非常**精确且友好**。<br>- 能够针对特定语言的常见陷阱进行优化。 | - 语法文件会变得**庞大臃肿**，维护成本高。<br>- 只能处理开发者**预见到**的错误，无法应对未知错误。 |
| **4. 全局纠错**<br>(Global Correction) | 计算错误输入与正确语法树之间的**最小编辑距离**（增、删、改最少符号数），将源程序转换为最接近的正确程序。 | - 理论最优，能给出**改动最小**的修复方案。<br>- 恢复效果最接近原始程序意图。 | - **计算复杂度极高**（时空开销巨大）。<br>- 在实际的大型工程代码（数万行）中**性能不可接受**，极少商用。 |
